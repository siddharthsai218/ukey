01 / the idea/ one less thing

A SECURITY KEY
SHOULDN'T BE
ANOTHER THING
TO LOSE.

Your phone already has a secure element, a fingerprint sensor, and a battery. uKey asks a simple question: why buy, carry, and lose a separate USB key just to prove who you are on Linux?

The answer is not “trust us.” It is a virtual HID device, the same CTAP2 protocol a hardware key speaks, and a key that stays inside Android's secure hardware. The parts that are not finished are printed right next to the parts that are.

Read the public status ledger

The trade-off, in plain language

+

No extra hardware

Your phone is the token. The host sees a normal hidraw device.

+

The key stays put

Android Keystore generates the P-256 key. The daemon only sees public keys and signatures.

!

Not a daily driver yet

Browser, SSH, and PAM paths are unverified or not implemented. The gaps are documented below.

01 / CREATE

A virtual USB token

The daemon opens /dev/uhid and asks the kernel for a HID device. Linux creates a hidraw node. No custom kernel module.

02 / SPEAK

CTAPHID + CTAP2

64-byte HID reports carry CBOR requests and signatures. The daemon handles channel IDs, fragmentation, keepalive, and cancellation.

03 / APPROVE

The phone signs

The Android app prompts for a strong biometric, then asks Android Keystore for an ES256 signature. The private key never crosses the bridge.

06 / security boundaries/ read this part

A SECURITY TOOL
SHOULD TELL YOU
WHERE IT BREAKS.

uKey is a prototype. It does not replace a dedicated hardware key for high-value accounts. These are the weak links the project knows about today.

Read the full threat model
01

Unauthenticated bridge

The signer socket has no TLS, authentication, or peer verification. --wireless exposes it on the LAN. Keep it on loopback via adb reverse.

02

Localhost pairing bypass

Local clients that skip the handshake are accepted as a Localhost Mock. The bridge is not a hard security boundary against a hostile local process.

03

No replay protection

A recorded signer response could be replayed in the current session model. Transport hardening is a roadmap item.

04

Metadata is unencrypted

RP IDs and credential IDs in credentials.json are readable by the local user and root. The private key is not exposed.

05

No independent audit

The Android app, biometric flow, and protocol handling are self-reviewed only. There is no attestation chain or vendor certificate.

06

No CTAP2 PIN/UV protocol

Biometric gating is app-local. The host cannot verify user verification through CTAP. Auto-lock is not a security control.

07 / what's next/ order matters, dates don't

CLOSE THE GAPS.
THEN EARN THE CLAIM.

The current prototype proves a kernel-level virtual FIDO2 token can exist. The next work is the part that makes it safe and useful every day.

01 / harden

Authenticated, encrypted bridge

TLS or an equivalent authenticated channel, peer verification, replay protection, and a real localhost boundary.

security

02 / protocol

U2F and resident keys

CTAPHID_MSG for pam_u2f, resident credentials, getNextAssertion, and a real attestation chain.

protocol

03 / integrations

Prove the workflows

Browser WebAuthn, SSH ecdsa-sk, and PAM/sudo with context approval. End-to-end tests, not demos.

workflows

04 / trust

Independent audit

An external review of the Android app and protocol edge, reproducible builds, and signed releases.

08 / run it/ fedora 43 · libfido2 1.15.0

BUILD THE
PROTOTYPE.

The verified path is a Fedora machine with /dev/uhid, Python 3.10–3.12, and libfido2 installed. The installer sets up udev permissions, a Python virtual environment, and a systemd user service with safe defaults.

  • Fedora 43 is the tested environment.
  • Other distributions use the manual setup path.
  • Android app is built from source in android/.
  • Wireless is opt-in and adds no transport security. Keep the bridge on loopback.
Open the repository Read the README
install · Fedora-tested path
# 1. clone
$ git clone https://github.com/ukey-sh/ukey.git
$ cd ukey

# 2. install the user service + udev rule
$ ./install.sh

# 3. verify the kernel sees a token
$ fido2-token -L
$ fido2-token -I /dev/hidraw6

Expected from step 3: a hidraw node, then FIDO_2_0 / ES256 details. The node name is assigned by the kernel and may differ. No success output is fabricated here.
