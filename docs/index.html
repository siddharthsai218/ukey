Architecture Overview

Engineered Different from First Principles

Why uKey succeeds where browser extensions, Bluetooth dongles, and cloud sync tools fail.

01 / KERNEL LEVEL

Virtual /dev/uhid Device

Not a browser extension. uKey registers a true USB Human Interface Device in the Linux kernel on usage page 0xF1D0. Any PAM module, OpenSSH client, or browser sees a physical hardware YubiKey.

BUS_USB • Native HID
02 / SILICON SECURITY

Android StrongBox Enclave

Private keys are generated directly inside tamper-resistant hardware (CC EAL5+). Keys never enter Android RAM and cannot be exported even on rooted devices.

NIST P-256 • Hardware Enclave
03 / ZERO-TRUST PROTOCOL

One-Time PIN Pairing

Single-use 6-digit PIN yields a persistent 256-bit token. All Wi-Fi handshake frames use HMAC-SHA256 nonces. Rogue devices on public networks are dropped in under 4ms.

Sub-4ms Rogue Rejection
04 / FAIL-SAFE INTEGRATION

0.0s Password Fallback

Phone out of battery or in another room? PAM sufficient fallback immediately prompts for your standard UNIX password with zero lag. You are never locked out of your machine.

Zero Lockout Risk

Technical FAQ

Frequently Asked Questions

How does uKey differ from mahirsn/passkey on Google Play? ▾
mahirsn/passkey relies on Bluetooth Low Energy (BLE) and USB. On Linux, BLE suffers from 1,500ms to 3,000ms latency, persistent BlueZ pairing dropouts, and is missing entirely on many custom desktop PCs. It also lacks native Linux PAM sudo integration and desktop session lock.

uKey utilizes Zero-Trust Wi-Fi LAN + USB with <5ms latency, single-use PIN pairing, native pam_u2f for instant terminal sudo, ecdsa-sk for git push, and native systemd session auto-lock.
Can uKey replace passwords and PATs when pushing to GitHub? ▾
Yes. OpenSSH natively supports FIDO2 security keys via the ecdsa-sk key type. Running ssh-keygen -t ecdsa-sk -f ~/.ssh/id_ukey requests a biometric touch on your phone. Uploading the public key to GitHub allows every git push to verify your fingerprint instead of asking for personal access tokens.
Can attackers on the same Wi-Fi sniff or replay my credentials? ▾
No. Your private key never leaves Android StrongBox hardware. Furthermore, Wi-Fi connections require a one-time 6-digit PIN pairing that yields a 256-bit device token. All handshake frames use HMAC-SHA256 challenge-response with random nonces. Unpaired connections are dropped by the daemon in <4ms.
What if my phone battery dies or is left in another room? ▾
You are never locked out. The PAM rule is configured with auth sufficient pam_u2f.so. If the phone is disconnected, or if you press Enter, Linux immediately falls back to your regular UNIX password with 0.0s delay.
Does my fingerprint biometric data ever leave the phone? ▾
Never. Biometric verification takes place entirely inside Android's BiometricPrompt and Keystore hardware. The laptop only receives the cryptographic ECDSA signature. No biometric imagery or templates ever cross the network.
