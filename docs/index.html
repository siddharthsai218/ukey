The short version. A security key is three things: a secure element, a transport, and an approval button. uKey asks whether those three pieces can live in different places — without the host noticing.
01 / The illusion

The kernel sees a key.
The key is a phone.

This is not a browser extension or a password manager. It is a virtual USB HID device, assembled from a HID report descriptor, a CTAP2 engine, and a remote signer. Here is the stack.

A file named /dev/hidraw

UHID lets a user-space process ask the Linux kernel to create a HID device. The kernel gives it a real hidraw node. Tools like fido2-token open it like any USB key.

UHID → HID → hidraw

64-byte reports

FIDO2 messages are larger than one HID report. CTAPHID splits them into 64-byte packets, then reassembles them on the way back. Channel IDs keep sessions apart.

CTAPHID framing

CBOR, not text

The CTAP2 layer parses CBOR maps for getInfo, makeCredential, and getAssertion. It returns status bytes the host already knows how to read.

CTAP2 + CBOR

The private key stays here

On the phone, a non-exportable P-256 key is created in AndroidKeyStore. StrongBox is preferred; TEE is the fallback. Software-backed keys are rejected.

AndroidKeyStore

One local socket

The daemon does not sign. It forwards the digest and relying party ID to a signer over a local TCP socket. Over USB, adb reverse keeps that socket on loopback.

JSON signer protocol

Proof, not vibes

The test harness uses the real fido2-token, fido2-cred, and fido2-assert tools. The repository also has 8 Python tests and an independent ECDSA check.

libfido2 + unittest
02 / One request

What happens when you touch the sensor.

A FIDO2 assertion is five short hops. None of them are magic; most of them are just framing.

01

libfido2 opens the device

fido2-token -L enumerates a device that looks exactly like a USB security key. The product string comes from the virtual HID device, not a USB descriptor.

host side
terminal
$ fido2-token -L
/dev/hidraw6: vendor=0x1209, product=0x0001
( uKey FIDO2 Authenticator )
02

The kernel carries 64-byte reports

When a response is ready, the daemon writes 64-byte input reports into UHID. The kernel delivers them to the hidraw reader. CTAPHID uses the first packet for channel, command, and length; continuation packets carry sequence numbers.

transport
ctaphid packet
first:  CID(4) | CMD(1) | LEN(2) | payload(57)
next:   CID(4) | SEQ(1) | payload(59)
// 64 bytes each, reassembled by the daemon
03

The daemon decodes CTAP2

A one-byte command plus a CBOR parameter map. getInfo reports FIDO 2.0 and ES256. The current caps field also reports nomsg — CTAP1/U2F messages are not implemented.

protocol
getInfo response (trimmed)
{
  "versions": ["FIDO_2_0"],
  "algorithms": [{ "alg": -7, "type": "public-key" }],
  "options": { "rk": false, "up": true, "uv": true }
}
04

The phone signs a digest, not a command

The signer receives the relying party ID and the digest to sign. On the phone, a per-use BiometricPrompt must succeed before the key is used. The key never leaves secure hardware.

secure element
daemon → phone
{
  "id": 7,
  "action": "get_assertion",
  "rp_id": "example.com",
  "digest": "9f2c…c41a"
}
05

The assertion comes back and verifies

AndroidKeyStore returns ASN.1 DER; the app decodes it to raw r || s. The daemon converts that raw signature back to DER at the CTAP2 boundary. fido2-assert -V then verifies it against the credential public key.

verification
terminal
$ fido2-assert -V -i assert_out cred_pub.pem
# exit 0: signature verifies against cred_pub.pem
# ES256 signature, P-256 public key

04 / The second act

Can the key show you what it’s signing?

FIDO2 signs a digest. A digest is not a command. The experiment is to capture the command context, show it out of band, and bind the approval to that exact context.

The obvious case is weak. If you are sitting at your laptop, you can already see the sudo command on screen. Showing it again on your phone adds ceremony, not value. Say that before anyone else does.

The case worth exploring is when the terminal is not the trust channel: a remote session, an unattended script, a shared machine, or a host you do not fully trust. There, the approval needs to arrive on a separate device, over a separate path, with the exact context attached.

01

Out-of-band, not on-screen again

The phone is a different device and a different display path. It can approve even when nobody is watching the terminal.

02

Bind the signature to the context

The phone would sign a hash of the canonical command, user, host, TTY, and cwd — not just “yes.” A changed command means a different signature.

03

Prove what was approved

The host can keep the context and the signature. That is evidence, not a scrollback buffer.

04

Survive the failure modes

TOCTOU, timeout, phone disconnect, password fallback, and a compromised host all need explicit answers. None of this is wired up yet.

The honest sentence: “For local sudo, you should just look at the terminal. This experiment is for the cases where the terminal is not the approval channel — and for the protocol problem of binding an approval to an exact command.”

06 / Boundaries

What this is not.

Most “why” questions disappear when the scope is explicit. This is a prototype and a reference implementation. It is not a product launch.

Not a YubiKey replacement

A dedicated key has a certified secure element, a button, USB/NFC, and a mature supply chain. uKey has a phone, a socket, and a lot of caveats.

Not a keychain or passkey manager

It does not store passwords, sync credentials, autofill forms, or recover your account. It performs an authentication ceremony; a keychain is a different product.

Not production-ready

The signer transport has no authentication or encryption. Credential metadata is stored unencrypted under ~/.config/ukey. There is no CTAP2 PIN protocol, attestation chain, or external security audit.

Not a phone plugged in as a USB gadget

The phone is not a USB device. The Linux daemon creates the virtual HID device; the phone is a remote signer over adb reverse or TCP.

What it is: a working virtual FIDO2 authenticator, a readable reference implementation, and an experiment about binding a local privilege request to an out-of-band signature. The interesting part is the implementation, not a category claim.
07 / Prior art

Standing on other people’s protocols.

FIDO2 is a standard. The virtual-device trick is not new either. Here is the honest comparison, including the project that is further along than this one.

ProjectWhat it doesHow uKey differs
YubiKey / NitrokeyDedicated FIDO2 hardware with a certified secure element, physical touch, USB/NFC.uKey replaces the hardware with a phone and a Python daemon. That is the experiment, not an upgrade.
mahirsn/passkeyAndroid phone as a FIDO2 key, with PAM, Bluetooth, resident credentials, StrongBox, and a Play Store app.More complete as a product today. uKey’s difference is a readable Python daemon on the Linux side and the context-approval experiment.
Platform passkeysTouch ID, Windows Hello, and Android biometrics perform WebAuthn ceremonies inside the OS.Linux lacks an equivalent platform authenticator. uKey is a roaming key, not a built-in OS feature.
libfido2The host-side library and tools used to talk to FIDO2 devices.uKey is the authenticator on the other end. It is tested with libfido2, not a replacement for it.
uKeyVirtual UHID device + CTAPHID/CTAP2 engine + Android signer + context design.The contribution is the readable implementation and the experiment. The protocol belongs to the FIDO Alliance.

If you want a daily driver, use one of the projects above. If you want to read how a FIDO2 key works — or help make the context experiment real — this repository is for that.

08 / Run it

The fastest way to see the virtual device.

Start with the mock signer. It is deterministic, it needs no phone, and it proves the host-side flow. The Android signer is the hardware path.

Linux + mock signer

Requirements: Linux with UHID enabled, Python 3.10+, cbor2, and fido2-tools for validation.

terminal
$ git clone https://github.com/siddharthsai218/ukey
$ cd ukey
$ python3 -m venv .venv
$ . .venv/bin/activate
$ pip install -r requirements.txt
$ sudo ./setup_udev.sh

# terminal 1: the virtual key
$ ./daemon/ukey_daemon.py --verbose

# terminal 2: a software signer for testing
$ ./daemon/mock_signer.py --verbose

# terminal 3: check what the host sees
$ fido2-token -L
Test double, not a security boundary. The mock signer’s keys are ephemeral and live in process memory. Do not use it for real credentials.

Android signer

Build the debug APK, install it, then expose the daemon’s loopback port over USB with adb reverse. Keep the phone unlocked while testing.

terminal
$ cd android
$ ./gradlew assembleDebug
$ adb install -r app/build/outputs/apk/debug/app-debug.apk
$ adb reverse tcp:8443 tcp:8443
# open the uKey app → 127.0.0.1:8443 → Start
Keep it on loopback. The signer protocol is unauthenticated and unencrypted. --wireless binds 0.0.0.0; only use it on a trusted network.

There Is No USB Key: Building a Virtual FIDO2 Authenticator

The host sees a real /dev/hidraw FIDO2 device. There is no USB key. The private key lives in an Android phone’s secure hardware, and a Python daemon translates CTAP2 requests into signer requests over USB or Wi-Fi. This talk walks through UHID, CTAPHID framing, CTAP2/CBOR, Android Keystore, and the test harness that proves it with fido2-token, fido2-cred, and fido2-assert. Then it covers the experiment that came next: can the phone display the exact sudo command and sign the context? Includes the gaps — U2F/PAM, transport security, resident credentials — and why “see what you sign” is harder than it looks. A prototype and reference implementation, not a product.

09 / Roadmap

The next honest steps.

No dates, no guarantees. The order is deliberate: make the claims true, then finish the demo, then widen compatibility.

Now

Make the prototype honest

Remove overclaims, align the README with the site, turn off wireless and auto-lock by default, and add a config surface that can be tested.

  • truth audit + tests
  • safe defaults, CI
  • 60-second demo script
Next

Make the context real

Add a small custom PAM module, capture the command context, show it on the phone, and bind the signature to a canonical digest.

  • approve / deny / timeout
  • test with a throwaway user
  • record the demo
Later

Widen compatibility

Only after the demo: CTAP1/U2F messages, real PAM integration, transport authentication, resident credentials, browser tests.

  • CTAPHID_MSG
  • transport auth
  • real-world WebAuthn
